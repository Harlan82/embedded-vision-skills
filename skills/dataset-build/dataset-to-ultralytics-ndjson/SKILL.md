# 本地数据集 → Ultralytics NDJSON（+ 平台可导入 ZIP）

> ## ⚠️ 上传平台时，必须传 ZIP，不要传 NDJSON
>
> **症状**：把 `.ndjson` 传上去，数据集里**所有图片都是裂的、加载不出来**。
>
> **原因**：NDJSON 每条记录的 `url` 是**图片的公开 http(s) 地址**，平台靠它回源拉像素。本地转换出来的 `url` 只能是占位路径（如 `images/foo.jpg`），公网上解析不到 → 全部 404。
>
> **不是编码问题、不是图片损坏**。ZIP 里的图片是原始字节，CRC 与 JPEG 结构都完好。
>
> **结论**：平台回传用 `images/ + labels/ + data.yaml` 的 ZIP；NDJSON 只作留档/版本快照。若坚持用 NDJSON 导入，必须先把图片托管到可公网访问的 URL，再填 `--url-prefix`。

> **一句话**：NDJSON 的标注语义与 YOLO 文本标签**完全同构**，转换是「重排 + 包一层 JSON」，**不该做任何坐标换算**。凡是需要换算的实现，都是理解错了格式。

## 一、先搞清下游，再动手（关键前置）

`url` 字段的取值取决于用途，**两种用途不通用**，先问清楚再跑：

| 下游 | 做法 |
|---|---|
| **回传 Ultralytics Platform** | NDJSON 是平台的**导出**格式；导入首推 **YOLO 结构 ZIP**（`images/` + `labels/` + `data.yaml`）。平台文档的格式自动识别里已列 NDJSON，但若导入报错，退到 YOLO ZIP 一定成功。 |
| **本地直接训练** | `yolo obb train data=x.ndjson` 走 `convert_ndjson_to_yolo`，它**按 `url` 用 aiohttp 下载**，不支持 `file://`；仅当 header 带 `path` 且目录为 `<ndjson目录>/<path>/images/<split>/<file>` 时才走本地拷贝分支。 |
| **纯本地训练且已有 txt** | 别绕 NDJSON——直接用 `images/`+`labels/`+`data.yaml` 更短。 |

**结论**：平台回传 → 同时产出 NDJSON 与 YOLO ZIP，用 ZIP 上传、NDJSON 留档。

## 二、NDJSON 格式规范（已对源码核实）

首行是数据集元数据，其余每行一张图：

```json
{"type":"dataset","task":"obb","name":"ds","description":"","bytes":<图片字节和>,
 "url":"","class_names":{"0":"class_1","1":"class_2"},"version":"latest",
 "created_at":"2026-01-01T00:00:00.000Z","updated_at":"..."}
{"type":"image","file":"a.jpg","url":"images/a.jpg","width":640,"height":640,"split":"train",
 "annotations":{"obb":[[0,0.48,0.352,0.568,0.356,0.572,0.4,0.484,0.396]]}}
```

- **OBB 的键名是 `obb`**（不是 `boxes`）：`[class_id, x1,y1,x2,y2,x3,y3,x4,y4]`，**归一化 0–1，顺时针，从左上角起**。
- `task` 取值：`detect` / `segment` / `pose` / `obb` / `classify` / `depth`。
- `detect` 用 `boxes`：`[cls, x_center, y_center, w, h]`；`segment` 用 `segments`（扁平顶点）；`pose` 用 `pose`。
- 其他键：`kpt_shape`（pose）、`depth_scale`（depth）。
- 转换器**不校验、不归一化、不裁剪坐标**，原样写入标签文件。所以归一化和取值范围得自己保证。

## 三、七个必踩的坑（按危害排序）

1. **跨会话文件重名（阻塞级）**。多次采集（如 `images/20260914_231401/` 与 `images/20260914_231958/`）各自从 `cam_000001` 编号，`file` 撞车 → 写盘互相覆盖 / 标注错配。**必须加会话前缀** `f"{session}_{stem}.jpg"`。
2. **平铺标签目录无法区分会话，而且会被最新会话覆盖**。`labels_obb/<name>.txt` 只按裸文件名索引，多轮采集的 `cam_000002.jpg` 会命中同一份标签。实测：第二轮采集写入后，`labels/` 与 `labels_obb/` 变成**只含最新会话的数百个文件**，旧会话的近三百份标签被静默覆盖。**解析顺序必须是「图片同级 txt 优先，平铺目录回退」**，并对两者做交叉校验。曾经因此凭空多出 2 个框（452 vs 450），也出现过 277 处不一致警告。
3. **不要相信 `meta.json` 里的尺寸**。那里写的常是**模型输入**尺寸，不等于落盘 JPEG 尺寸。直接解析 JPEG SOF 段拿真实宽高。
4. **别用严格正则统计行数**。用 `^\d+ (0|1)\.\d{6} ...$` 这类模式数标签行，会漏掉小数位不同的行，得到偏小的总数，进而误判转换正确性。**用「按空白切分后字段数 == 9」来判定**。
5. **零样本类别**。`classes.txt` 里存在、但标注中 0 个实例的类别（本次是 `class_8`）会让模型学不会它、并拉低 mAP。要么补数据，要么删类重映射。
6. **Windows「- 副本」重复项（会静默翻倍）**。采集包被多次拷贝到同一目录时，Windows 会把冲突文件改名成 `cam_000001 - 副本.jpg`。**它不是无用的副本** —— 实测其字节与**另一个会话**的正式图完全相同（即别的会话的数据被拷进了本会话目录）。`convert.py` 早期版本只过滤 `.preview`，会把这类图**计入第二次**：本次一百九十余张的数据集被算成二百二十余张、框数 561 被算成 667。现已在 `DERIVED_MARKERS` 里加 `- 副本` 一并过滤。**发现这类文件先别删** —— 先按 md5 比对来源，它可能是用户有意合并的第二批数据。
7. **无标签孤儿图 ≠ 负样本**。采集被中断时会留下「有图、没有 txt、采集日志里也没有这一行」的孤儿（本次 `20260916_212009/cam_000037.jpg`）。若按「无标注」放进去，YOLO 会当**背景图**训练，而它画面里其实有物体 → 制造假阴性。**必须剔除**（或先补标），不要当负样本。

## 四、验收基线（缺一不可）

转换后必须核对，数字对不上就是有 bug：

- `images` 记录数 == 实际图片数（排除 `.preview.jpg` 之类衍生图）
- `box` 总数 == 标签文件非空行总数 == 采集日志 / meta 里的统计值
- `file` 字段全局唯一
- 所有坐标 ∈ [0,1]，`len(row) == 9`（OBB）或 `5`（detect）
- ZIP 内 `images/<split>` 与 `labels/<split>` 的 stem 集合**差集为 0**
- 类别分布直方图 —— 顺手就能发现零样本类与极端不均衡
- **与 `采集日志.csv` 对账**（采集类数据集强烈建议）：日志里每行都写了 `图片` 绝对路径、`目标数`、`字节`。把日志的会话分组计数与磁盘上的 `cam_*.jpg` 数一一比对，能抓出两类问题：
  - **有图无日志** = 孤儿图（见坑 7），必须剔除而不是当负样本；
  - **有日志无图** = 文件在拷贝/传输中丢了。
  本次对账：212009 磁盘 37 / 日志 36 → 揪出 `cam_000037.jpg`；212456 磁盘 122 / 日志 122 → 干净。
  > 注意日志可能出现**重复表头行**（采集程序重跑一次就写一次表头），用 `图片` 字段含 `/` 与否过滤掉，别把它当成数据行。

## 五、用法

```bash
python scripts/convert.py \
  --root "./work/aaaproject/特调/特调" \
  --out-ndjson special.ndjson \
  --out-zip special_obb_yolo.zip \
  --val-every 10
```

常用参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--root` | 必填 | 数据集根目录 |
| `--task` | `obb` | `obb` 或 `detect`（决定注解键名与每行字段数） |
| `--label-dir` | 自动探测 | 平铺标签目录，如 `labels_obb`、`labels` |
| `--classes` | 自动探测 | `classes.txt`（`<id> <name>` 每行）或 `data.yaml` |
| `--val-every` | `10` | 每 N 张取 1 张作 val，按文件名 md5 取模 → 确定性且时间上交错，避免相邻帧泄漏 |
| `--url-prefix` | 空 | 空则 `url="images/<file>"` **占位，不可用于平台导入**；填公网前缀才可导 |
| `--sessions` | 全部 | 只保留指定会话（逗号分隔），如 `--sessions 20260915_033054`。多轮采集里剔除某一批时用 |
| `--exclude-sessions` | 无 | 排除指定会话，优先级低于 `--sessions` |
| `--images-only` | 关 | **只打包图片（无标注）**：不读也不写 `labels/`，ZIP 仅含 `images/<split>/` + `data.yaml`，NDJSON 省略 `annotations` 键 |

**脚本会在写出占位 URL 的 NDJSON 时打印醒目警告**。看到该警告 = 这份 NDJSON 不能直接上传平台。

## 五-补、`--images-only`：没有标注时「回传图片、平台内标注」

采集拍回来的包常常**只有 `images/` + `train.txt`，没有任何标签**（MaixCAM 抓的 `666.zip` / `666+.zip` 都是这形态——**`train.txt` 只是文件名清单，不是标签**，别被文件名骗了）。此时先判断要哪种交付：

| 需求 | 做法 |
|---|---|
| **A. 先自动标注再转** | 用已有的 `.mud`/ONNX 跑伪标签（转完按第六节体检），再走正常转换 |
| **B. 只回传图片、平台内手工标注** | 用 `--images-only` |

```bash
python scripts/convert.py --root <dir> --images-only --val-every 0 \
  --name dataset-b --out-zip "./work/dataset-b_images_only.zip"
```

**关键设计（勿改）**：
1. **绝不能写空的 `labels/*.txt`**。YOLO 语义里**空 txt = 负样本 / 该图无目标**，是真实训练信号；而我们要的是「**未标注、待标注**」，两者语义完全不同。写空 txt 会污染数据。
2. 因此 `--images-only` **完全跳过 `labels/` 的读写**，ZIP 只含 `data.yaml` + `images/<split>/`。
3. `data.yaml` 仍写出**类别名**，平台内标注时类别已预置、不用重敲。类别名来源同正常流程（`classes.txt` / `data.yaml`）；**若该包本来没有，需自带一个 `classes.txt`**（可抄同形状族模型的 `names` 元数据）。
4. NDJSON **省略 `annotations` 键**（而非 `annotations: {obb: []}`）——省略才表示「未标注」。
5. `--val-every 0` 全进 train：待标注的数据不该预先切 val。

**验收数字（2026-09 实测）**：62 张 320×320 JPEG → `images entries=62 / labels entries=0 / CRC OK / 与源逐字节一致（62 比对 0 不符）`；NDJSON 63 行（1 表头 + 62 图）、无 `annotations` 键、`file` 全局唯一。

## 六、OBB 伪标签质量体检（模型自动标注必做）

采集数据多半是**模型自动标注的伪标签**（如 MaixCAM 跑 `.mud` 量化模型 + 低置信阈值）。上线训练前先体检，否则会把系统性错误当数据喂进去。

**三个可自证的指标**（脚本层级，不需要人工看图）：

| 指标 | 算法 | 判读 |
|---|---|---|
| 直角偏差 | 四个顶点相邻边的夹角与 90° 之差，取最大值 | 真 OBB 应接近矩形。中位 ~0.6° 正常；均值 >5° 或 90 分位 >20° 说明有整批坏框 |
| 对边平行度 | `abs(s0-s2)/max(s0,s2)` 与 `abs(s1-s3)/max(...)` | OBB 应是矩形或平行四边形；长期 >0.2 说明顶点是**独立回归**出来的散点，非矩形化输出 |
| 蝶形/点序 | 相邻边叉积是否同号（凸性） | 出现非凸 = 顶点**顺序写错**（如 TL,TR,BL,BR），是转换器/采集端 bug，必须修 |
| 绕向 | 有向面积符号 | 全 CW 或全 CCW 正常；混合 = 点序不一致 |
| 越界 | 任一坐标 ∉ [0,1]（容差 2%） | 只能是微量越界；成片越界 = 用了像素坐标没归一化 |

**关键关联分析（最容易定位根因的一步）**：把「坏框」与「是否贴边（顶点距边界 <2%）」交叉统计。

实测案例：1954 框中 464 框直角偏差 >20°，而这 464 个**全部**是贴边目标（贴边 466 个里歪 464 个，**99.6%**；内部 1488 个**零**歪斜），且面积全部小于 100×100 px。结论明确：**被画幅裁切的目标，模型的角点回归失效，产生退化四边形**。

据此可选的处置（按侵入性排序）：
1. **提高采集时的标注置信阈值**（如 0.35 → 0.5+），从源头减少低质量框；
2. **丢弃贴边框**，或**先裁切再标注**避免目标被切；
3. **矩形化重建**：对每框顶点求 `minAreaRect`，把退化四边形拉回真矩形（会损失形状信息，仅在确认要矩形时用）；
4. 若整体偏置（框形状对但有位移），另查采集端是否存在**帧与推理结果不同步**（保存的图 vs 实际推理的帧）。

> 注意：体检发现的质量问题**不等于转换有 bug**。先跑上面的几何指标，若蝶形=0、绕向一致、坐标在 [0,1]，则转换是忠实的，问题在标注源头。

**val 切分为什么用 md5 取模**：采集数据相邻帧高度相似，按顺序切尾部会把「最后一整段视频」全丢进 val，指标虚高。哈希取模能零散打散、可复现、无需保存随机状态。

**顺带查重复项**：采集包经多次拷贝常混入 `xxx - 副本.jpg`（Windows 冲突改名）。**别当垃圾直接删** —— 实测这批文件不是冗余复制品，其 md5 与**另一个会话**的正式图逐字节相同，即「别的会话的数据被拷进了本会话目录」，且 `cam_NNNNNN` 序号会与本地图撞车。处置前先按 md5 比对来源，并向用户说明「这可能是你有意合并的第二批数据」。

### 增强数据（灰度/翻转）与 train/val 泄漏 —— 增强流程必查

给数据集做增强（如随机 20% 转黑白、翻转、加噪）后，**同一场景会存在多份孪生图**。`convert.py` 的 split 是 `md5(完整 fname) % val_every`，孪生图文件名不同 → 哈希相互独立 → **一个进 train、另一个进 val**，验证集里出现「训练时见过的同一场景」，mAP 虚高。

实测（2026-09，特调 122 图 + 24 张灰度 = 146 图）：

| 取模依据 | train / val | 彩色-灰度孪生被拆散 |
|---|---|---|
| 完整 fname（默认） | 133 / 13 | **4 对** |
| scene key（去掉 `_bw`） | 131 / 15 | **0 对** |

**做法**：增强图统一加固定后缀（`_bw` / `_gray` / `_flip`），切分时对 **scene key**（如 `file.replace("_bw.jpg", ".jpg")`）取模，而不是对整名取模。转换后写个 <30 行脚本重写 `split` 字段并重建 ZIP 即可 —— ZIP 布局保持与 `convert.py` 一致：`data.yaml` + `images/<split>/<session>_<stem>.jpg` + `labels/<split>/<session>_<stem>.txt`（**labels 用带会话前缀的 stem**，最容易写错）。

**这不是 `convert.py` 的 bug** —— 它不感知「哪些图是同源孪生」，增强流程必须自己保证。

**其余两条增强经验**：
1. **挑 20% 的方式**：按 `md5(fname)` 升序取前 `round(N*0.2)` 张，确定性、可复现、无需保存随机状态（与 split 的哈希思路一致）。
2. **灰度图存 `mode="L"` 单通道 JPEG**（真剥除色度，质量 95）；Ultralytics 读入后会自动 stack 成 3 通道，可直接与彩色图混训。标签**原样复制**成 `xxx_bw.txt` 即可，OBB 归一化坐标与分辨率无关，无需任何换算；空 txt 也要照抄（空 = 负样本，语义不能丢）。

## 六-补3、NDJSON → 按 (类别, 颜色) 均衡的灰度增强子集

需求形态：「把数据集里每个形状、每个颜色的图各抽 20% 转黑白，且各组合张数要均衡」。
彩色几何体数据集（红/绿/蓝塑料件）做灰度增强时，**颜色是独立于类别的第二个维度** ——
不做均衡就会出现「某颜色某类别特别多」的偏斜。

用 `scripts/color_balance_gray.py` 一条命令跑完下载→判色→均衡抽样→灰度化→ZIP：

```bash
python scripts/color_balance_gray.py \
  --ndjson "./work/cam-000207.ndjson" \
  --dest   "./work/demo" \
  --zip    "./work/demo_yolo.zip" \
  --per-group 40 --work-dir "./work"
```

### ⚠ 判色：绝不能用 bbox 中心取色

这类数据的物体**放在白色/浅灰平台上**，且**常有镂空件**（如 `hollow_class_9` 镂空形状H，中心就是洞）。
中心取色两个场景都必错。正解见 `bbox-attr-sampling` 技能 —— **背景弃权 + 属性投票**：

```
if 饱和度 S < S_MIN  或  亮度 V < V_MIN:   弃权（白平台、灰影、黑阴影）
else:                                     按色相投票判 红/绿/蓝
```

实测参数（`cam-000207`，480×480，白色形状I）：`S_MIN=0.28`、`V_MIN=0.22`。
**结果 4398/4398 全部判出、0 失败、纯度全部 ≥0.85**，镂空件零误判。

> **别用标准纯色色相当目标值。** 实测三峰是 红 ~0°、**绿 ~140°**、**蓝 ~210°** ——
> 塑料件的绿偏青、蓝偏天蓝。写 120/240 会让绿/蓝的色相偏差达到 20°~30°，
> 物体与背景混色时更容易翻边。判完务必打一次**全数据集色相直方图**确认峰的位置与个数
> （只有 3 个峰 = 确认无第四色；出现第 4 个峰说明有待处理的其他颜色）。

### 「20%」与「均衡」的冲突 —— 必须让用户拍板

组合数 = 类别数 × 颜色数。各组合原始张数不可能相等，于是：
- 「每组各抽 20%」→ 张数 = `round(0.2n)`，**天然不均衡**（本次 33~82，差 2.5 倍）；
- 「各组合张数完全相等」→ 需要定一个统一 `T`，`T` 不同总产量差很多。

**别自己猜，把真实分布摆出来让用户选。** 本次三选项与用户选定：

| 口径 | T | 总量 | 评价 |
|---|---|---|---|
| 典型组 200 的 20% | **40** | **840** | ✅ 用户选：19/21 组恰好 20%，完全均衡 |
| 最小组的 20% | 33 | 693 | 严格不超 20% 上限，但大组利用率低（8%） |
| 各组自身 20% | 33~82 | 881 | 最贴字面，但完全不均衡 |

**做法**：先算 21 组真实计数 → 打印成表格 → 用 `AskUserQuestion` 给 3 个口径（附总量与偏差）→ 再执行。

### 无标注记录要主动点明

`annotations` 键缺失的图**没有类别、也没有框**，既无法判色也无法做检测训练样本，
**不能当负样本**（见坑 7）。本次 6 张，全部剔除并在报告中列出文件名，请用户去平台补标。

### 验收基线（`cam-000207` 实测，八百余张）

- `images == labels == 840`，两向差集 **0 / 0**
- 21 个组合**各 40 张，偏差 0**
- 灰度图 **mode 全部 = `L`**（单通道，真剥除色度；若拿到 `RGB` 说明只做了视觉灰化，色度还在）
- 标签与 NDJSON **逐条比对 0 处不一致**，0 个空标签
- ZIP：仅 `data.yaml` + `images/` + `labels/`，`CRC OK`，22.3MB
- 两份视觉回归：判色回归（7类×3色 画框，21 格全对）+ 灰度回归（确认无残留色彩、框仍贴合）

> 交付结构给 `images/ + labels/ + data.yaml + sampling_manifest.csv`——
> 只给灰度图不给标签，这批数据对训练毫无价值。
> 命名用 `{cls}_{color}_{idx:05d}.jpg`：自文档化（看一眼就知道属于哪个组合）、文件系统安全
> （原始 `file` 字段常含空格与括号，如 `cam6._000001 (63).jpg`，直接沿用会踩坑）。

## 六-补4、把 NDJSON 划分 train/val/test：采集连拍段才是最大泄漏源

> 已封装为 `scripts/split_ndjson_balanced.py`（会话/帧号解析 → 连拍段切分 → 分层比例 → 段内连续块 →
> 孪生跟随 → NDJSON/清单/段清单/报告）。命令示例见本节末。**核心判据与踩坑见下，改脚本前先读。**

需求形态：「划分验证集和测试集，注意数据均衡，每个颜色和类型 10%/5%，保证训练真实可信」。
**动手前必须先查采集结构**，否则做出来的划分会让 val 指标虚高到没有意义。

### 第一步：解析会话与帧号，切「连拍段」

采集类文件名一般自带会话前缀与帧号，两种形态都要覆盖：

```python
m = re.match(r"^(.*?)\s*\((\d+)\)\.jpg$", name)   # cam6._000001 (63).jpg
if not m: m = re.match(r"^(cam[0-9._]*?)_(\d+)\.jpg$", name)   # cam_000599.jpg
```

把彩色原图按 `(会话, 帧号)` 排序，再对 `(会话, 类别, 颜色)` 做**游程切分** → 每段 = 一次物体摆放连拍。

**实测真实结构（`demo-yolo`，数千张）**：全部只来自 **数十段**！
`cam6` 千余帧只有 **6 段**（每段约 200 帧）、`cam` 五百余帧只有 **3 段**。
即操作员把物体放好、手动旋转连拍约 200 帧，再换下一个。

### 第二步：判「段内帧是否近重复」—— 千万别用全图描述子

| 描述子 | 结论 | 对不对 |
|---|---|---|
| 64×64 / 16×16 **全图** 灰度 | 段内 max/adj ≈ 1.2 →「几乎全同」 | ✗ 被**静止背景稀释** |
| **bbox 裁切 24×24**，去均值除标准差 | 同段内相隔 ≥20 帧 ≈ 跨段（比值中位 **0.97**） | ✓ |

**结论：判"帧是否近重复"必须只取物体区域。** 全图距离里背景是常量，会把所有差异压扁。
实测这批数据段内物体**在手动旋转**，帧有真实姿态多样性，**不是纯冗余**。

> 顺带一个坑：**别用 bbox 中心当「物体是否被重新摆放」的判据**。这批是模型伪标签，
> 框中心逐帧抖动 **6%~34%**（比真实的摆放位移大一个量级），完全不可用。

### 第三步：量化泄漏，再把选项摆给用户

帧级 md5 随机切 10%/5% 的实测后果：
- **67% 的 val 帧，其 train 最近邻就在同一次摆放（同段）内**；86.6% 同会话
- 「±2 帧内有 train 邻帧」= **98.8%**

**致命约束**：只有 14/21 个 `(类别,颜色)` 组合拥有 ≥2 段，**7 个组合只有 1 段**。
所以「每组合 10%/5% 均衡」与「不跨段切分（零泄漏）」**数学上不可兼得**。必须让用户拍板：

| 口径 | 组合覆盖 | 比例 | 泄漏 |
|---|---|---|---|
| 均衡优先 | 21/21 | 精确 10%/5% | val/test 与 train 同段同摆放 |
| 可信优先（段为最小单元） | 14/21 | 实测约 30%/22%（段粒度 200 帧，不可控） | **0** |
| 折中（20 帧块为单元） | 21/21 | 精确 | 相邻帧不跨 split，但同段上下文仍共享 |

### 若用户选「均衡优先」，务必用「段内连续块」而不是打散乱抽

在**每个组合的每一段内部**按比例取连续块：`train = 段首`、`val = 中段连续块`、`test = 段尾连续块`。
这样 val/test 只会在块的**边界**处与 train 相邻，而不是每张 val 图旁边都有一张 train。

**实测效果**：「±2 帧内有 train 邻帧」从 98.8% → **13.3%**，同时保持 21/21 覆盖与精确比例。

### 验收基线（`demo-yolo` 实测）

- train 4439 (84.75%) / val 530 (**10.12%**) / test 269 (**5.14%**)
- 每组合 val% 偏离 ≤ **0.70** 个百分点、test% ≤ 0.58；**21/21 组合全覆盖**
- 增强孪生（`_bw`）与其彩色原图 **0 处** 不同 split —— **这条是硬要求，必须校验**
- 三 split stem 互不相交；images/labels 两向差集 0/0
- ZIP 仅 `data.yaml` + `images/{train,val,test}/` + `labels/{train,val,test}/`，CRC OK
- 视觉回归：val/test 各抽 12 张画框

### 三个必踩的实现 bug

1. **val 块与 test 块重叠**：`idx_test = idx_val = n` 之后各自从 `n` 往回走 → val 实际只拿到 `vb - tb` 张，
   症状是 **val% 恰好是期望值的一半**。正确写法：先走 test 得到 `idx_test`，再 `idx_val = idx_test` 往回走。
2. **增强孪生挂载单遍扫描会漏**：孪生图可能排在彩色原图**之前**（实测漏四百余张）。
   必须两遍：先收集全部彩色 scene，再挂孪生。
3. **`%` 格式化字符串里的百分号**：`"...val 10% / test 5%..."` 会被当成格式符，报
   `unsupported format character '/'`。要写 `%%`。

### 附带交付：连拍段清单

生成一份 `burst-inventory.csv`（session/cls/color/帧区间/各 split 张数/pure 标记）。
**只挑 `pure=是` 的段**（整段同 split）即可组成一个**完全不泄漏**的评估集 ——
这是给用户日后自查、或做「诚实指标」复核用的，成本极低、价值很高。

## 六-补、反向转换：平台导出的 NDJSON → 可回传 YOLO ZIP

平台**导出**的 `.ndjson` 要变回 ZIP，用 `scripts/ndjson_to_zip.py`（与 `convert.py` 方向相反）。

```bash
python scripts/ndjson_to_zip.py \
  --ndjson "./work/top (1).ndjson" \
  --out-zip "./work/top_detect_yolo.zip" \
  --work-dir "./work/_top1_work" \
  --fallback-dir "./work/top (1)/images" \
  --workers 16
```

**与正向的四个关键差异**：
1. **split 直接沿用 ndjson 的 `split` 字段**，不重新做 md5 取模。平台里的 train/val 划分是用户已经在平台上调好的，重切会破坏它。
2. **图片按 `url` 下载**。平台导出给的是**签名 CDN 直链**（`https://cdn.ul.run/ap/i/<hash>.jpg?Expires=...&Signature=...`），有效期约 **7 天**。**这是权威副本**——同一文件名在平台上的字节与本地采集目录里的**不一样**（实测 3/3 MD5 全不同，平台侧显然重新编码过）。**若本地也有同名图片目录，不要图省事直接用它**：平台侧的图才与标签一一对应。
   - `--fallback-dir` 仅在下载失败时兜底；本次八百余张 0 失败、0 尺寸不符，未触发。
3. **`task=detect` 用 `boxes`，标签写 `cls cx cy w h`（5 字段）；`task=obb` 用 `obb`（9 字段）**。字段数由 task 决定，同样是纯重排、零换算。
4. **无 `annotations` 键的记录 → 不写 label 文件**（区别于「空 txt = 负样本」）。

**⚠ 平台导出的两种「无标注」要分清**：
- **整个键不存在**（`"annotations"` 都没有）→ 该图在平台上**未标注**。实测 `top (1).ndjson` 813 条里有 **8 条**这种，且经肉眼核对**这 8 张图里明明有物体**（形状D+形状F、形状A+形状B…）。
- 键存在但列表为空（`{"boxes":[]}`）→ 平台认为该图**无目标**（负样本）。

**这是个真实风险**：那 8 张若按「无 label 文件」处理，Ultralytics 会当**背景图**训练，等于教模型「这些物体是背景」→ 制造假阴性。交付时要主动向用户点明，并给两个选项：① 补标注；② 从数据集中剔除。**不要默默放过去。**

**验收基线（本次实测）**：813 图 → 805 label / 1434 框；**逐条与 ndjson 比对的 label 文本 0 处不符**；5 字段 100%、越界 0；`images - labels = 8`（即上述 8 张未标注）、`labels - images = 0`；CRC OK。
**最后一定要做视觉回归**：把标签画回图上看框是否贴合（本次 6 图抽样全部紧贴目标，类别色标一致）——这是唯一能发现「图与标签错配」的检查，结构校验过了也仍要做。

## 六-补2、NDJSON → **Pascal VOC** zip（平台支持的第二/三种导入格式）

平台「从本地导入数据集压缩包」其实支持**三种**结构，别默认只有 YOLO：

| 导入格式 | 压缩包结构 | 说明 |
|---|---|---|
| YOLO | `images/` + `labels/` + `data.yaml` | 见上文 `ndjson_to_zip.py` |
| **Pascal VOC** | **`images/` + `xml/`**（同名配对） | **本节的 `ndjson_to_voc.py`** |
| COCO | `annotations.json` | 未提供脚本 |

> **踩坑**：需求方要的是 VOC 格式（平台规范：`images/` + `xml/`、同名配对、≤3000 张、≤500MB），却先给了 YOLO txt 版本 → 被退回「标签数据全丢」。**「标签全丢」往往不是转换 bug，而是格式选错了**——平台按结构自动识别，给错结构就识别不到标注。**接手前先问清目标格式**，或直接看用户给的平台截图。

```bash
python scripts/ndjson_to_voc.py \
  --ndjson "./work/top (1).ndjson" \
  --out-zip "./work/top_voc.zip" \
  --stage "./work/_voc_stage" \
  --max-images 3000 --workers 16
```

**VOC 规范要点（逐条对齐平台要求）**：
1. zip 内**只有** `images/` 与 `xml/` 两个文件夹，无多余文件（实测 `anything else: none`）。
2. **一张图片对应一个同名 xml**（`.jpg` ↔ `.xml`，stem 相同）。实测两向差集都是 0。
3. **坐标是 1-based 闭区间像素值**，需 `clamp` 到 `[1,W]`/`[1,H]`——这是与 YOLO 归一化格式唯一的实质差异，也是唯一需要算的地方：
   `xmin=(cx-w/2)*W` 四舍五入后 clamp；`xmax<xmin` 时交换；退化框（宽或高为 0）丢弃。
4. `size` 的 `width/height/depth` 取**图片真实值**（JPEG SOF 解析），不是 ndjson 里的值；`depth` 用通道数（RGB=3）。实测八百余张 size 全部相符。
5. `≤3000` 张、`≤500MB` 为平台硬限，脚本对超量做截断并打印忽略数。
6. **坐标往返误差应 ≤ 1px**：本次 1434 框，最大归一化误差 `3.12e-3` = **0.9984 px**（即四舍五入的固有误差，均值 7.3e-5）。若误差显著大于 1px，说明换算写错了。

**⚠ 同样要处理的「无标注」问题**：缺 `annotations` 键的记录会生成**空 `<object>`** 的 xml（`<annotation>` 里除 size 外无 object）。VOC 语义下「无 object」= **负样本/背景图**。实测本包八百余张里有 **8 张**这种，而**肉眼核对这 8 张图里明明有物体**——直接把背景标签喂给训练会制造假阴性。**必须向用户点明并让其选择（补标注 / 剔除）**，不要默默交付。

**验收基线（2026-09 实测）**：813 jpg + 813 xml / 1434 框 / CRC OK / 配对差集 0 / size 100% 相符 / 结构问题 0 / 坐标往返 ≤1px。**最后做视觉回归**：把 xml 的 bndbox 画回图上看是否贴合（本次 6 图抽样全部紧贴目标、类别名与物体一致）。

## 六-补5、YOLO ZIP → Pascal VOC：**先分清是哪一种 VOC**

说「转成 Pascal VOC」时，**必须问清是哪种布局**，两者不通用，选错就是我的技能里记过的那个事故：
平台报「标签数据全丢」——**那不是转换 bug，是格式选错了。**

| 布局 | 结构 | 适合 | 代价 |
|---|---|---|---|
| **标准 VOC** | `JPEGImages/` + `Annotations/` + `ImageSets/Main/{train,val,test}.txt` | LabelImg / MMDetection / torchvision / 自研工具 / 存档 | 无 |
| **平台导入版** | 扁平 `images/` + `xml/`（同名配对） | Ultralytics 平台「从本地导入」 | **≤3000 张、≤500MB 硬限；丢掉 train/val/test 划分**（平台自行切分） |

**脚本**：`scripts/yolo_zip_to_voc.py`（两种都出，`--flat` 切平台版，`--max-images 2900` 截断到平台硬限内）

```bash
# 标准 VOC（保留划分）
python scripts/yolo_zip_to_voc.py --src-yolo-zip demo-split-yolo.zip --dst-zip demo-voc.zip
# 平台导入版（注意 3000 张上限）
python scripts/yolo_zip_to_voc.py --src-yolo-zip in.zip --dst-zip out_flat.zip --flat --max-images 2900
```

### 坐标约定与「框不要有错」的验证做法

VOC 的 `bndbox` 走 **1-based 闭区间像素**（VOC devkit 原始约定）：

```
xmin = round((cx - w/2) * W)    xmax = round((cx + w/2) * W)     clamp 到 [1, W]
ymin = round((cy - h/2) * H)    ymax = round((cy + h/2) * H)     clamp 到 [1, H]
x2<x1 交换；面积退化的框丢弃。W,H 从 JPEG SOF 读，不用任何元数据。
```

> ⚠ 有工具（如 LabelImg）内部把 bndbox 当 0-based，会差 1 px 的框宽。**视觉上完全一样**，
> 交付时把这句话写进 README，省得对方以为框错了。

**验证必须是「逐框往返比对」，不能只看数量**：生成每个 XML 后**立刻重新解析**，反算回归一化坐标，
与源标签逐框比较，取最大误差（单位换算成 px）。**实测 5238 框：x 侧最大 0.9024 px、y 侧 0.7856 px，
均值 0.011 px，clamp/swapped/degenerate 全为 0** —— 这才能说「框没错」。
同时校验：`size(W,H)` 与真实图相符、`object` 数与标签行数一致、类别名与 `classes.txt` 对得上、
`ImageSets/Main/*.txt` 与源划分集合相等。把这份报告作为 `CONVERT_REPORT.txt` **打进包里**一起交付。

### 三个实测坑

1. **平台会把单通道灰度图重编码成三通道。** 本地明明是 `mode=L` 的灰度 JPEG，从平台导回来全是
   **depth=3**（R=G=B）。写 README / 校验 `depth` 时**要按实际字节读**，别按本地认知写 depth=1。
2. **Windows 上 `zipfile` 句柄没关时 `os.replace` 会报 `PermissionError: [WinError 5]`。**
   凡是「先写 zip、再回读校验、最后替换」的两遍写法都会踩。**改成单遍：边写边把校验做完，
   报告用 `zo.writestr()` 在同一个 zip 里补上**，就不需要 replace。
3. **别把校验脚本命名成 `inspect.py` / `copy.py` / `types.py`** —— 它会遮蔽标准库同名模块，
   表现为 `numpy` 导入时报 `module 'inspect' has no attribute 'cleandoc'`。改名即可。

## 六-补6、数据集超过平台上限：**均衡缩容，不要截断**

需求形态：「这个包太大了，帮我删到 3000 张以下」。
**Ultralytics 平台 VOC 导入有 3000 张硬上限**，超了直接拒收。但**不能简单截断**：

| 截断方式 | 后果 |
|---|---|
| 取前 N 张 | 类别分布偏斜，拍摄会话（session）被整段砍掉 |
| 随机抽 N 张 | 同一次「摆放连拍」的帧被抽散，黑白孪生被拆家 |

用 `scripts/subsample_voc_balanced.py`：

```bash
python subsample_voc_balanced.py \
  --src-voc-zip demo-voc.zip \
  --attr-csv demo-split-manifest.csv \
  --total 2900 --keep-split \
  --out-flat  demo-voc-flat-2900.zip \
  --out-split demo-voc-split-2900.zip
```

内置口径（四条都要有，缺一条就会复现上表的坑）：
1. **抽样单元 = scene**（一次摆放；彩色原图与其黑白孪生同进同出），灰度占比保持不变；
2. **按类别分层，每类配额相等** → 子集是「按类均衡」，不是「总量均衡」；
3. 类内**跨 session 按可用量分配**，段内**等间隔取**（不是只取每段开头几百帧）；
4. `--keep-split` 时 **val/test 全保**，只缩 train。

验收基线（本数据集 5238 → 2898 实测）：每类极差 ≤5；黑白占比 16.3% 保持不变；
图片字节与源包**完全一致**；flat 版 XML 与源仅 `<folder>/<path>` 两行不同；孪生 0 拆家。

**文件名陷阱**：清单 CSV 里常是**原始名**（`cam5_000001 (661).jpg`），zip 里是**清洗名**
（`cam5_000001_661.jpg`）。脚本内置 `clean_stem()` 兜底匹配并打印命中率 ——
命中率不是 100% 就说明分组键错了，别硬跑。

**flat 还是标准？** 见「六-补5」：平台导入要 flat（`images/` + `xml/`，同名配对）；
本地 LabelImg / MMDetection 要标准（`JPEGImages/` + `Annotations/` + `ImageSets/Main/`）。
两版一起出成本极低，别让用户二选一时返工。

## 七、平台上传要点
- 平台数据集进入 **Ready** 需同时满足：train 至少 1 张、val 或 test 至少 1 张、至少 1 张有标注。
- 若只给 train，平台会自动把部分 train 挪到 val —— 顺序不可控，**建议自己显式切好 val**。
- 架构 ZIP/TAR，不做逐文件上传；`data.yaml` 放在压缩包根目录且命名规范（`data.yaml`/`dataset.yaml`）。
- **导入格式（以平台规范为准）**：平台「从本地导入数据集压缩包」当前支持 **YOLO**（`images/`+`labels/`+`data.yaml`）、**Pascal VOC**（`images/`+`xml/` 同名配对）、**COCO**（`annotations.json`）三种结构，按结构自动识别。
  > 早期此处曾写「平台不导入 Pascal VOC XML」——**该结论已作废**。用户提供的平台规范截图明确列出 Pascal VOC 结构，且给了硬限：zip ≤500MB、≤3000 张、`images/`+`xml/` 同名配对。**导入前务必先确认目标格式**（见「六-补2」）。
- 同内容图片按 XXH3-128 去重，重复上传不额外占配额。

## 八、拿训练好的模型回跑评测：**平台面板的数字不能直接信**

交付数据集之后，用户常拿着训练结果回来问「这指标真实吗」。**第一步永远是本地复算，不要读面板。**

### 8.1 实测事故：面板的 mAP50-95 显示成了 mAP50

某个 YOLO26s（Ultralytics Platform 训练）的 `model-a.onnx`，面板显示：

```
mAP50 99.3%   mAP50-95 99.3%   Precision 99.3%   Recall 99.2%
```

本地用**同版本** `ultralytics 8.4.166` 复算（val 五百余张 / test 二百六十余张）：

```
val : P=0.987  R=0.990  mAP50=0.991  mAP50-95=0.924
test: P=0.994  R=0.996  mAP50=0.994  mAP50-95=0.914
```

四个指标里三个对得上（≤0.6 点），**只有 mAP50-95 差 7~8 个点 —— 面板把它显示成了 mAP50 的值。**

> **后果**：用户和我都据「mAP50 与 mAP50-95 差距过小」推断「框被背下来了 / 记忆化」。
> 真实比值是 `0.914/0.994 = 0.92`（COCO 上 YOLOv8 系列约 0.70~0.76），属于"任务很简单"的合理范围，
> **该论证作废**。教训：面板上任何一格数字都要本地复算，尤其是 mAP50-95。

### 8.2 复算流程与两个必踩坑

```bash
# 坑1：pip 必须先清代理，否则报 "Could not find a version that satisfies the requirement"
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY python -m pip install ultralytics

# 坑2：data.yaml 里的 `path: .` 是按【当前工作目录】解析，不是按 yaml 所在目录
cd <解压后的数据集根目录> && python ../run_val.py
# 否则报 FileNotFoundError: ... images not found, missing path '<CWD>\images\val'
```

`yolo val model=xxx.onnx data=data.yaml split=val imgsz=<与训练一致> conf=0.001 iou=0.7 max_det=300`
（`val` 模式默认 conf=0.001 是为了算 mAP，**不是部署阈值**。）

> ultralytics val 收尾时会触发沙箱的安全删除拦截器，进程可能带 `SystemExit` 结束 →
> **结果必须边跑边落盘**（每跑完一个 split 就写文件），别等脚本末尾统一写，否则白跑。

### 8.3 独立实现可作交叉验证（实测差 ≤0.7 点）

不必依赖 ultralytics，自己写 onnxruntime + NMS + COCO 101 点 AP 就够：
实测 test `mAP50=0.9950 / mAP50-95=0.9147 / P=0.9961 / R=0.9962`、val `0.9843 / 0.9174`，
与官方**差 ≤0.7 点**。YOLO 导出 ONNX 的坐标格式要先实测确认（本模型是 **cx,cy,w,h 像素 + 已 sigmoid 的类别分**）。

### 8.4 三个 split 用同一套解码一起评 —— 泄漏的直接证据

| split | n | mAP50 | mAP50-95 |
|---|---|---|---|
| TEST（全量） | 269 | 0.9950 | 0.9147 |
| VAL（全量） | 530 | 0.9843 | 0.9174 |
| TRAIN（抽样 1200） | 1200 | 0.9888 | 0.9238 |

**test > train、三者无差异** → 直接证明 val/test 测的是训练分布，不是泛化。
这比任何间接推理都硬，成本只有多跑一遍推理。

### 8.5 归因探针：区分「认形状」与「找斑块」

**① 色块置换（最有价值，成本极低）**：把物体框内区域填成同色纯矩形 ——
**位置、大小、颜色全保留，形状信息全毁**。实测：

```
mAP50 0.9950 -> 0.1257
位置命中但类别变了 77.0%    仍以同一类别命中 20.4%    位置对不上 2.6%
置换后最高置信度中位数 0.9391   （形状毁了，它依然很自信）
```

→ **定位靠"找非白斑块"（97.4% 仍命中正确位置），分类靠形状（77% 类别翻转）。**
一句话把"偷懒"拆到了机制层面。

**② 干扰块**：在平台另一侧贴一块纯色矩形。实测 **140/数百张图产生额外虚假检出（52%）**，
而 mAP50 几乎不变（0.9950→0.9948）——
**AP 对低置信 FP 不敏感，是指标盲区**；必须按部署 `conf` 阈值单独报 FP 率。

**③ 几何扰动探针（缩放/平移）：设计不当会给出假结论。**
把图像平移后只保留仍在画幅内的 GT，**等于先把最难定位的边缘目标筛掉**，
于是 mAP50-95 假性升到 0.9930/0.9948（恰好等于各自的 mAP50，因为剩下的框全部在 IoU≥0.95 命中）。
**正确做法：基线与扰动必须用同一批图**（对同一子集分别算），否则测的是筛选效应而不是模型行为。
> 识别信号：**扰动后 mAP50-95 恰好等于 mAP50** —— 这说明各 IoU 阈值下的匹配数完全相同，
> 通常只可能是"匹配的框 IoU 全 ≥0.95、未匹配的全 <0.5"，几乎必是筛选造成的。

**④ 部署视角单独报**：`conf=0.25` 下的检出率（类别正确且 IoU≥0.5 命中 GT），
而不是只报 mAP。实测 268/269 = 99.63%。这是用户真正关心的口径。
