# Redpoint Grid Checker（红点检测日志网格校验）

## Overview

将相机多帧检测日志（同一物理红点被反复框出、带 ±15~25px 抖动）整理为"真实坐标"，
判定这些点是否构成一个规整的 N×M 网格（常见为 3×3、相机约 45° 俯拍透视），
并渲染空间排布图、算出每个点的最优坐标。

**三条来自用户反馈的硬原则（务必遵守）：**

1. **用户不要"一个结论"，要"看到分布自己判断"。** 默认先给**点云透明核对视图**
   （每个原始检测点画成小彩点 + 小的绿色中心标记 + 拟合网格），让用户直接看抖动云、
   看点云是否贴住网格。网格"结论"只是辅助参照，绝不能只甩一个 verdict 就声称数据可信。

2. **绿色大框太碍眼 → 不画大框。** 实践中反馈"绿框太大"。所以 visualize 只画一个
   **小绿点/小绿圈**标记聚类中心（r≈3.4），点云才是绝对主角。不要把检测框画成实心大矩形。

3. **内部自洽 ≠ 真实位置正确。** 脚本判定"规整 3×3"只代表点彼此成网格、抖动稳定，
   不代表坐标绝对值对你的真实摆放正确（标定/ROI/NMS 系统性误差会让所有框整体偏移却仍"很规整"）。
   **最终真值必须回 MaixCAM 原帧（检测框叠加）核对。**

核心脚本：
- `scripts/visualize_redpoints.py` —— **点云透明核对视图（优先做）**：彩色小点=各帧原始检测（按簇着色，展示抖动/分布），小绿点(圈)=聚类中心标记，浅蓝虚线=拟合网格。**不画大绿框。**
- `scripts/cluster_redpoints.py` —— 干净网格判定视图：绿框真坐标 + 蓝/橙内/外点 + 判定结论。
- `scripts/compute_coords.py` —— **最优精确坐标计算**：聚类→双线性拟合得 (row,col)→按左上→右下排序，输出每点实测质心(±σ)、理想网格位、n、时间覆盖率、置信等级。

## When To Use

- 用户贴出 `[红点]` / `cx= cy= w= h= score=` 形式的多帧检测日志，要求"理一下/画出来/看看是不是规整的 3×3"。
- 用户给出预期形状（如"应该是一个很规整的 3×3"），需要程序化验证数据是否可信。
- 交付时应给出**全部原始检测点的分布**（不只是聚合结果），由使用方自行判断。
- 用户要每个物理点的精确坐标（用于对照真实摆放、写标定表等）。

## Quick Start

第 1 步 · 点云透明核对视图（**必做，让用户看到原始分布**）：
```bash
python scripts/visualize_redpoints.py <input_log.txt> [--eps 35] [--target 3 3] [--maxpp 10000]
```
- `--maxpp 10000`：关闭子采样，**画出全部原始点**（用户要看完整分布时用）。默认 70（大簇子采样省渲染）。
- 输出 `<input>_overlay.html`：彩色小点=各帧原始检测（按簇着色，点云散开程度=该点检测抖动/不稳定范围）；**小绿点(圈)=聚类中心标记（无大框）**；浅蓝虚线=拟合网格。

第 2 步 · 干净网格判定视图（结论参照）：
```bash
python scripts/cluster_redpoints.py <input_log.txt> [--eps 35] [--target 3 3]
```
输出 `<input>_grid.html`：绿框真坐标 + 蓝/橙内/外点 + 判定结论。

第 3 步 · 最优精确坐标（用户要逐点核对时用）：
```bash
python scripts/compute_coords.py <input_log.txt>
```
（默认读 `redpoints_log.txt`。）输出按左上→右下排好的 9 点坐标表，并写 `coords_result.json`。
`visualize_redpoints.py` **直接 import 本模块**复用同一套聚类/拟合/坐标逻辑，确保图上的坐标表、
绿点旁标注的 (cx,cy) 与 `coords_result.json` 三者编号完全一致（见下方 ⚠️ 第 4 条）。

参数说明：
- `--eps`：聚类距离阈值。默认 35.0；同一物理点多帧抖动落在此半径内即合并。
  太小会把一个真实点切成多个簇（如 30 切出 12 簇），太大则把不同点并掉，需据实测微调。
- `--target 3 3`：用户预期的网格形状，仅用于结论文字与"是否吻合预期"判定；拟合本身会
  自动搜索所有 R×C（R*C==N）组合取残差最小的，不受此参数限制。
- 两个 HTML 均深色主题，可直接在浏览器/预览面板打开核对。

## Workflow（脚本内部，供理解与排错）

1. **解析**：正则提取每行 `cx/cy/w/h/score`，统计原始帧数 `raw detections`。
2. **聚类去重**：以距离阈值 `EPS` 做"最近簇运行平均合并"，把同一物理点的多帧抖动合并成
   一个真坐标（含出现次数 `n`、平均框尺寸、平均置信度、该簇所有命中行号）。输出 `distinct clusters = 真实点数 N`。
3. **间距估计**：对每个簇取最近邻距离，取中位数作为 `spacing`。
4. **网格拟合（旋转无关）**：
   - 对所有满足 `R*C==N` 的 (R,C) 及两种主轴方向，做"按主排序切列→列内按 y 排成行"的分配。
   - 对每种分配做双线性最小二乘拟合 `x=a0+a1*i+a2*j+a3*i*j`（y 同理，4×4 方程带奇异保护），
     计算每点残差，取**平均残差最小**者为最佳网格。双线性模型天然吸收约 45° 旋转，
     不依赖 PCA（PCA 在直线/旋转网格上会失效）。
   - 残差 ≤ `spacing*0.8` 判为网格内点（蓝），否则异常点（橙）。
5. **时间覆盖率（判定真伪的关键，来自实战）**：
   - 对每个簇记录首/末命中行号，`coverage = (last-first)/总行数`。
   - **n 极小(如 1)且 coverage≈0%** → 该点只在一两帧出现 = **单帧闪现**，最可能是误检/瞬态，**最不可信**。
   - **n 小但 coverage≈100%** → 全程都在、只是每帧常漏检 = **真实但检测弱**。
   - 例：某日志 9 簇中 8 个 coverage 94~99%（真实），仅 1 个 n=1 且 coverage=0%（单帧闪现）。
6. **最优坐标估计（compute_coords.py）**：
   - **实测质心 (cx,cy)**：多帧检测在高斯抖动下，样本均值是位置的最大似然/最小方差估计 → **最精准的实际检测坐标**。附带 ±σx/±σy 作为不确定度。
   - **理想网格位 (ideal_x,ideal_y)**：双线性拟合给出"若严格成规则网格"的坐标，是规则化参照（会平滑掉真实偏差）。
   - 若用户物理摆放是严格规则的 3×3，用理想网格位；若要核对实际检测位置，用实测质心。
7. **渲染 SVG/HTML**：点云透明视图用小绿点标记中心（无大框）；干净视图用绿色实框；浅蓝虚线=拟合预期网格（已校正旋转）。

## 判定结论与解读

- `R==3且C==3且R*C==N且max_res<spacing*1.2` → "规整 3×3（旋转约45°）— 数据内部自洽"。
- 否则若 `R*C==N` 且最大残差达标 → 规整但形状非预期。
- 否则 → "不规整 / 有错"，说明点数对不上或存在严重离群。
- **但以上都只是"内部自洽"结论**（见下方 ⚠️ 警示），必须由原帧复核确认坐标绝对值。

## ⚠️ 关键警示（务必遵守，曾踩坑）

**脚本判定"规整 3×3"仅代表数据内部自洽，绝不等于与用户真实物理摆放一致。**

- 若相机标定 / ROI 裁剪 / NMS 阈值存在系统性错误，会使所有框整体偏移、旋转或缩放——
  此时网格仍可能"非常规整"，但全部画错位置。
- 若用户反馈"你画的跟实际摆放非常不一样"，那就是系统性误差信号：**不要**再用本脚本的
  自洽结论声称数据可用，应回设备核对标定/ROI/坐标变换。
- **顶部/边缘点经常"没框"通常是检测器灵敏度问题（ROI 边缘、反光、俯仰角），不是几何问题。**
  用时间覆盖率区分：若这些点 coverage≈100% 只是 n 小，说明真实存在但每帧漏检，应去调检测器；
  若 coverage≈0%（单帧闪现），才是疑似误检，需回原帧确认。
- 最终真值 = MaixCAM 原帧（检测框叠加）。本脚本只能告诉你"点彼此是否成网格、抖动是否稳定"，
  不能证明坐标绝对值正确。

4. **旋转约 45° 时 (row,col) 编号是"完美平局"——必须固定约定，否则同一份日志跑出两套编号。**
   - 实测：对于约 45° 旋转的 3×3 网格，`by_x=True` 与 `by_x=False` 两种主轴朝向的
     双线性拟合残差**完全相等**（如都是 9.092）。若两个脚本各自独立做网格搜索、仅靠
     浮点 `<` 做 tie-break，会因微小浮点差异选到相反朝向，给出一个镜像的两套 R/C 编号。
   - **解法（已落地）**：`visualize_redpoints.py` 与 `compute_coords.py` 共用 `compute_coords.run()`
     这一个计算核心；并在 `search_best()` 里写死确定性 tie-break——残差相差 >1e-9 取更小者，
     平局（Δ≤1e-9）固定取 `by_x=False`（与历史 `coords_result.json` 一致）。这样无论何时跑、
     跑哪份脚本，编号都稳定一致。**不要**在两个脚本里各写一份网格搜索。
   - 延伸：既然 45° 旋转下 (row,col) 本就无物理"左上角"起点，R/C 仅是网格拓扑序号；
     真正给用户的硬数据永远是那 9 个 `(实测X, 实测Y)`，R/C 仅用于组织表格。

5. **SVG 渲染必须用图像坐标（Y-down），绝不能翻成数学坐标（Y-up）——否则整图上下镜像。**
   - 坑：早期版本 `sy(y)` 写成 `MT + (ysmax - y)/(ysmax - ysmin)*PH`（Y-up），导致整张点云图/绿框图
     被**垂直镜像**：Y 越大（检测框越靠下）反而画到越靠上，与 MaixCAM 原帧、与用户看到的"下/上"完全相反。
     用户反馈"你的图跟我的反着/上下颠倒"就是此症状。
   - **正确写法（已落地）**：`sy(y) = MT + (y - ysmin)/(ysmax - ysmin)*PH`（Y-down，与检测输出一致）。
     绿框图里 box 上边沿也必须是 `sy(cy - h/2)`（**减号**），不是 `cy + h/2`。
   - 自检：数据 `y_min`→屏幕顶部、`y_max`→屏幕底部；R1C1（最小 y）在顶部、R3C3（最大 y）在底部。
     若不满足，先查 `sy` 是不是被写成了 Y-up。注意：坐标**数值**不受影响（仍是多帧均值），只是图被镜像。

## 输出文件说明

- `*_overlay.html`（点云透明核对视图，**优先给**）：彩色小点=各帧原始检测（同一颜色=同一物理点，点云散开程度=该点检测抖动/不稳定范围）；**小绿点(圈)=聚类中心标记（无大框）**；浅蓝虚线=拟合网格（各团应整体贴线、彼此等距）。
- `*_grid.html`（干净网格判定视图）：绿框真坐标 + 蓝/橙内/外点 + 判定结论。
- `coords_result.json`（compute_coords 输出）：按左上→右下排序的 9 点坐标、n、覆盖率、置信。
- 终端同时打印每个簇的真坐标、n、置信度、coverage，以及最佳网格 R×C、残差、异常数，便于无图时快速核对。

### 让用户自己判断的读图要点（写在 overlay 图下方）
1. 每个颜色的点云应聚成一小团（抖动小=稳定）；若某团拉得很长/发散，说明该点检测不稳。
2. 小绿点(圈) 标记该色点云的聚类中心，应大致落在点云中心。
3. 各团应整体贴住浅蓝虚线网格、彼此等距——若某团明显偏离线或间距异常，即证明该处数据有错。
4. 判定真伪看两件事：**n（命中帧数）** 与 **时间覆盖率**（首末命中行号跨度/总行数）。n 极小且覆盖率≈0% 的是单帧闪现（最不可信）；n 小但覆盖率≈100% 说明全程都在、只是每帧常漏检（真实但弱）。
5. 本图只证明"点彼此是否成网格、抖动是否稳定"，坐标绝对值是否正确要看设备原帧。
